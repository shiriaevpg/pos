# ПОС - преподавательская оценка студентов

Консольное приложение на Java 17+: студенты, рубрикатор критериев, оценки, итог, выгрузка.
Хранилище - в памяти (порты позволяют заменить на файл/БД без правок домена).

## Запуск

```bash
# Maven
mvn test                                  # юнит-тесты
mvn -q compile exec:java                  # интерактивный режим
mvn -q compile exec:java -Dexec.args=--demo   # сквозной сценарий

# без Maven
javac -encoding UTF-8 -d out $(find src/main -name "*.java")
java -cp out ru.mipt.pos.Main --demo      # демо
java -cp out ru.mipt.pos.Main             # интерактивно (help - список команд)
```

Демо (`--demo`) проходит весь сценарий: студенты и критерии → оценки → отказ на «12 из 10» и на критерий вне
рубрикатора → исправление и отмена оценки → итог → экспорт в CSV и JSON.

## Структура и зависимости

```
domain          ← ни от чего не зависит (ни CSV, ни консоли, ни DI)
  model         Student, Criterion, Rubric, Evaluation, EvaluationFactory, Score, Weight, *Id, FinalGrade
  service       FinalGradeService + GradingStrategy (WeightedAverage, GradedOnly, Rounded)
  repository    порты: StudentRepository, RubricRepository, EvaluationRepository
application     PosFacade (сценарии), порт ReportExporter
infrastructure  InMemory*-репозитории, CsvReportExporter, JsonReportExporter
ui              ConsoleApp (разбор команд и вывод)
di + Main       контейнер и composition root - единственное место, где всё собирается
```

Зависимости направлены внутрь: `ui → application → domain ← infrastructure`.

## Карта DDD

**Ubiquitous Language** - классы и методы названы словами из ТЗ: `Student`, `Criterion` (`maxScore`, `weight`),
`Rubric`, `Evaluation`, `Score`, `FinalGrade`; «итог» - `FinalGradeService`, «рубрикатор» - `Rubric`.

| Что | Тип | Почему |
|---|---|---|
| `Score`, `Weight`, `StudentId`, `CriterionId`, `FinalGrade` | Value Object | неизменяемы, сравниваются по значению; `Score(7)` ≡ `Score(7)`; сами отсекают мусор (отрицательный балл, NaN, пустой id) |
| `Student` | Entity | идентичность - `StudentId`, имя не определяет «кто это» |
| `Criterion` | Entity (внутри `Rubric`) | идентичность - код критерия |
| `Evaluation` | Entity, свой агрегат | идентичность - пара (студент, критерий); балл и комментарий **исправляются**, а оценка остаётся той же - это и есть признак сущности |

**Границы агрегатов.**
- `Rubric` - корень: охраняет «критерии уникальны» и «оценивать можно только критерий из рубрикатора».
- `Evaluation` - отдельный агрегат: оценок много, меняются независимо от рубрикатора, поэтому внутрь `Rubric`/`Student`
  их не кладём. На студента и критерий ссылается **по id**, а не по объекту.
- `Student` - отдельный агрегат (пока почти пустой - по ТЗ достаточно ядра).

**Инварианты и где они охраняются**
- `балл ∈ [0, max]` - `Criterion.ensureAccepts`, вызывается и из конструктора `Evaluation`, и из `Evaluation.correct` (исправить тоже нельзя за пределы);
- `критерий из рубрикатора` - `Rubric.criterion(id)` (бросает `DomainException`), вызывается из фабрики;
- `итог согласован с оценками` - итог **не хранится**, а вычисляется в `FinalGradeService` при каждом запросе; сервис также отвергает чужие оценки и оценки по неизвестным критериям.
- Конструктор `Evaluation` package-private: создать оценку в обход `EvaluationFactory` нельзя.

**Repository** - три узких порта в `domain.repository`, реализации в `infrastructure`.
**Domain Service** - `FinalGradeService`: правило затрагивает два агрегата (оценки + рубрикатор), ни одному не принадлежит.

**Модель итога.** Итог - проценты 0..100: `Σ(score/max · weight) / Σ weight`. Сколько стоит неоценённый критерий -
решение предметной области, поэтому это сменяемая стратегия (ниже).

## SOLID

- **S.** `Evaluation`/`Rubric` - только правила; `PosFacade` - только оркестрация; `ConsoleApp` - только ввод/вывод;
  экспортёры - только форматирование. Файл/CSV/консоль в домене не встречаются.
- **O.** Новое правило итога - новый класс `GradingStrategy`; новый формат выгрузки - новый `ReportExporter`;
  новый критерий - данные, не код. Существующие классы не правятся.
  *Компромисс:* новый экспортёр придётся зарегистрировать в `Main` (одна строка), а `ConsoleApp.handle` - обычный
  `switch` по командам; для прототипа это дешевле, чем реестр команд.
- **L.** Все `GradingStrategy` соблюдают один контракт: результат в `[0, 100]`, пустой набор оценок → 0. `RoundedStrategy` его
  не нарушает (проверено тестами) и подставляется вместо любой стратегии.
- **I.** Вместо одного «IGodRepository» - три порта по агрегатам; `ReportExporter` - один метод.
  *Компромисс:* внутри `EvaluationRepository` четыре метода - но они связны, дробить на Reader/Writer было бы декоративно.
- **D.** Application и domain зависят от интерфейсов (репозитории, стратегия, экспортёр). Граф собирается в `Main` через `Container`.
  *Компромисс:* `PosFacade` зависит от конкретного класса `FinalGradeService`, без интерфейса: точка вариативности уже есть
  (`GradingStrategy`), интерфейс над сервисом был бы «пустым ради галочки».

## Паттерны GoF

| Группа | Паттерн | Где | Какую боль закрывает |
|---|---|---|---|
| Порождающий | **Фабрика** | `EvaluationFactory.create` | Единственный способ создать оценку: проверяет принадлежность критерия рубрикатору и диапазон балла. Без неё эти проверки разъехались бы по UI/сервисам. |
| Структурный | **Фасад** | `PosFacade` | Консоли нужен один объект со сценариями, а не знание о трёх репозиториях, фабрике и сервисе. Заменяем UI (веб/бот) - сценарии не переписываем. |
| Структурный | **Декоратор** | `RoundedStrategy` | Округление подмешивается к любой стратегии без изменения и без дублирования кода в каждой. |
| Поведенческий | **Стратегия** | `GradingStrategy` | Правило итога - сменяемое: «неоценённое = 0» (`WeightedAverage`) против «считаем только оценённое» (`GradedOnly`). Меняется одной строкой в `Main`. |

Шаблонный метод, билдер и т. п. сознательно не брали: боли, которую они закрывали бы, в этом коде нет.

## DI-контейнер и тесты

`di.Container` - минимальный контейнер (привязка тип+имя → фабрика, ленивые синглтоны), используется только в `Main`.
Своя реализация - осознанно: на ~35 строк, без зависимостей и рефлексии; при желании заменяется на Guice/Spring
в одном файле, потому что ни один класс вне `Main` про контейнер не знает.

`PosTest` (JUnit 5, 11 тестов): балл > max, отрицательный балл, граница max, критерий вне рубрикатора, исправление
с нарушением инварианта, дубликат критерия, обе стратегии (включая «нет оценок»), декоратор округления, чужая оценка в итоге.
